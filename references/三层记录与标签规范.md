# 三层记录与标签规范

## 三层记录法（每条时间轴条目的固定结构）

```
事实层：做了什么（一句话，动词开头）
思路层：当时怎么想、依据什么判断 —— 前缀"想："
变化层：什么触发了转向/放弃/升级为规则 —— 前缀"变："（仅思路变动时写）
```

**写入示例**

```
10-15  完成 OPC 入驻系统 MVP 并上云（app.py + opc.db，单次会话 87 分钟建成）
       想：开工前先读完入驻文档、回答"能否实现/难度多大"三个问题，把思路对齐做在写代码之前。
       变：验证出"先对齐思路再施工"比直接开工快一个量级，遂固化为交付铁律【阶段0：思路对齐】。
```

**顺序不可颠倒**：先事实、后思路、再变化。思路层是账本的价值所在，禁止用事实层敷衍。

## 思路层的诚实规则（硬约束）

| 情况 | 处理方式 |
|---|---|
| 思路来自真实对话 | 正常写入 |
| 思路来自用户口述 | 正常写入，注明"（口述）" |
| 思路从历史记忆还原 | 写入并标"（记忆还原）" |
| 思路无法还原 | 写"**思路待补：**<待用户补充的问题>"，严禁编造 |
| 从未讨论过 | 不写思路层，只写事实层 |

**判断句式**：能填"因为当时想到 X"才写；只能填"大概是 X"就不写。

## 标签词典

只使用以下标签，不自造：

| 标签 | 用于 |
|---|---|
| 推进 | 常规进展，无思路转向 |
| 决策 | 做出了影响后续的选择 |
| 转向 | 改变了方向或放弃了原方案 |
| 验证 | 用事实检验了一个假设（无论通过与否） |
| 卡点 | 被真实阻塞：外部依赖、缺资源、能力不足（须写清阻塞源） |
| 教训→规则 | 从踩坑提炼出可复用规则，**必须同时写出规则本身** |

**判断不准时的默认选择**：宁可打"推进"，不要打"卡点"。把"卡点"留给真正的外部阻塞。

### 卡点的两种类型（防自审铁律的关键）

```
主动取舍：因为 A 比 B 更重要而推迟 B →  正常记录，不打标签
被动失控：没有任何取舍依据就滑过去了 →  记录时写"变："，交用户确认是否定性
```

**禁止**在未与用户确认的情况下，把一次推迟判定为"失控"或"失信"。

## 项目卡"思路主线"

每张项目卡展开后的第一行，一句话概括该项目思路演进的主题，随演进而更新。

- 写得出的标准：读完这一行，能理解这个项目一路是怎么走到现在的
- 例：`从"先做出来再说"到"先对齐思路再施工"，前期靠 AI 补盲区，后期靠 SOW 锁范围`

## 承诺-变化-原因-调整 四元组

用于记录"言而无信"这类情况。**目的是复盘，不是审判**。

```
承诺：10-15 说过要把 6 张能力卡片全部写完
变化：截至 10-21 只完成 2 张
原因：（用户填写或口述，不得代填）
调整：改为按项目优先级排序，先写可复用的 2 张，其余进入待办
```

**判定纪律**：不写"你又食言了"，只写四元组本身。**不得**在账本中使用"言而无信""破戒""烂尾"等评判性词汇作为标签或结论。

## AI 建议的写法（只基于事实）

每条建议必须满足：

1. 给出事实依据（来自项目登记表、扫描结果、时间轴，注明出处）
2. 直接指出问题，不用委婉铺垫
3. 可执行（有明确下一步动作）
4. 不捧杀、不敷衍、不无依据表扬

**允许批评，禁止表扬代替诊断**。若当期无实际问题，写明"本期未发现需纠正项"，不要凑数。
